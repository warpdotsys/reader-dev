# JAR audit batch 3: seven correctness fixes and one structural improvement

Seven discrepancies between the decompiled JAR (reader-pro-3.2.14) and the source are resolved in this commit: a missing data-class field (`pdfImageWidth`), a missing predicate (`isLocalPdf`), a boolean inversion in `JSONTable.save`, a signature upgrade for `forEachUser`, a new `saveBookConfig` endpoint, a TTS route alias, and an internal `cacheBookOnServer` overload. The `editShelfBook` return type is changed from `Unit` to `Book?` to support `saveBookConfig`'s response semantics.

**Watch for:** `saveBookConfig` handler contains unreachable GET-param logic since only a POST route is registered (confirmed); `cacheBookOnServer(JsonArray, String)` has no caller in the codebase (confirmed — dead code until the next batch wires it); existing `editShelfBook` call sites now silently ignore the new `Book?` return value, which is fine but worth verifying no future caller expects non-null (likely).

## High-level view

The `JSONTable` boolean fix is the most impactful correctness change: every `onCheckEnd` callback in the system was receiving inverted `isNew` semantics, meaning CURD subclasses that distinguish insert from update were doing the wrong thing. The fix is a single `!` operator in two call sites.

The `forEachUser` signature now matches the JAR's suspend+Boolean contract. The implementation wraps iteration in `coroutineScope` and breaks on `false`, enabling callers to short-circuit. No current call sites exist in-tree, so this is forward-compatible wiring.

`saveBookConfig` adds a POST-only endpoint that sets `pdfImageWidth` on an existing shelf book. The handler has an unreachable GET branch (dead code) because the route is registered only as POST. The endpoint depends on the `editShelfBook` return-type change to propagate the updated book back to the client.

The new `cacheBookOnServer(JsonArray, String)` overload iterates a list of book URLs and caches all chapters for each. It is intended as an internal helper for batch caching (the commit message says "供 cacheBookSSE 内部调用") but is not yet wired. The method duplicates the caching loop from the existing `RoutingContext` overload.

## onCheckEnd boolean inversion (JSONTable)

The CURD interface defines `onCheckEnd(entity: T, isNew: Boolean, allData: JsonArray)`. Before this fix, `JSONTable.save` and `saveMulti` passed `found` — which is `true` when the entity already existed. The fix inverts to `!found`, aligning with the `isNew` contract. Any CURD subclass that used this boolean for conditional post-save logic (e.g. incrementing counters for new entities, skipping updates for existing ones) was silently doing the opposite.

## saveBookConfig endpoint and editShelfBook return type

The handler includes a branch for GET method query-param parsing:

```kotlin
if (context.request().method() == HttpMethod.POST) {
    bookUrl = context.bodyAsJson.getString("bookUrl") ?: ""
    pdfImageWidth = context.bodyAsJson.getFloat("pdfImageWidth", 0f)
} else {
    bookUrl = context.queryParam("bookUrl").firstOrNull() ?: ""
    pdfImageWidth = context.queryParam("pdfImageWidth").firstOrNull()?.toFloatOrNull() ?: 0f
}
```

The route registration is POST-only: `router.post("/reader3/saveBookConfig")`. The `else` branch is dead code. If the JAR also registers it as POST-only, this is cosmetic noise. If the JAR has a GET alias, it's missing here.

The `editShelfBook` return-type change from `Unit` to `Book?` is source-compatible — Kotlin callers that previously ignored the return (all existing call sites) continue to compile without changes. The null case occurs when the book isn't found in the shelf array, which `saveBookConfig` handles with `?: bookInfo` fallback.

## cacheBookOnServer internal overload

The method has no callers in the current tree. The commit message indicates it's "供 cacheBookSSE 内部调用" but `cacheBookSSE` still uses its own inline caching loop with SSE progress reporting. This is dead code until a subsequent commit wires it.

`chapters.getString(i)` assumes every element in the JsonArray is a raw string (book URL). No type guard exists; a non-string element would throw a `ClassCastException` at runtime. If the JAR's caller always passes a string array this is safe in practice, but a `try/catch` or type check would prevent opaque failures if the contract drifts.
