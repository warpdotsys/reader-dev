# JAR audit round 5: missing methods and BookSourceController expansion

This round adds seven methods identified by comparing decompiled JAR signatures against source: PDF rendering helpers (`convertPdfToImage`, `convertPdfPageToImage`, `savePdfPageToImage`), shelf-save logic (`saveBookToShelf`), cover download (`saveBookCover`), an RSS permission gate (`canEditRssSource`), and the `getContextPath()` abstract/override pair. It also adds substantial new functionality to BookSourceController (batch save with limits, source map generation, remote fetch) and refactors `BaseController.saveUserSession` to self-load the user map instead of requiring callers to pass it.

**Watch for:** PDDocument resource leak in `convertPdfPageToImage(Book, ...)` (confirmed). `saveBookToShelf` constructs file paths from unsanitized `book.name` and `book.author`, opening a path-traversal vector (confirmed). `convertPdfToImage(Book, Boolean)` is a stub returning `true` unconditionally — callers in `saveBookToShelf` treat this as a success signal (confirmed). `saveBookCover` dereferences `source!!` after a code path that can produce null (confirmed).

## High-level view

The PDF rendering pipeline gained three helpers that mirror JAR signatures, but `convertPdfToImage(Book, Boolean)` is an empty stub. It returns `true` without doing any work, which means books imported as PDFs via `saveBookToShelf` will appear to succeed without generating any page images. The single-page variant `convertPdfPageToImage(Book, Int, Boolean)` does real work but never closes the `PDDocument` it opens.

`saveBookToShelf` is a 130-line method extracted from the existing `saveBook` HTTP handler. It uses `book.name + "_" + book.author` directly in `Paths.get(...)` without sanitization — unlike `FileController` and `UserController` which apply canonical-path checks. This is the same path-traversal gap that was already addressed in other controllers in earlier rounds.

`saveBookCover` uses a forced non-null assertion (`source!!`) on the return value of `getBookSourceStringBySourceURLOpt`, which can return null when a book's origin URL doesn't match any stored source. The catch block around it swallows the NPE silently, so cover download simply fails without feedback.

The `BaseController.saveUserSession` refactor internalizes user-map loading, removing a parameter from all callers. The change introduces a declared `userMutex` field that is never locked, suggesting incomplete concurrency work.

`BookSourceController` gains batch-save, source-map generation, and a new `saveFromRemoteSource` handler that duplicates `readRemoteSourceFile` except for adding an auth check. The `canEditBookSource` and `canEditRssSource` permission gates are defined but never called — they exist to match JAR signatures, not to enforce access control yet.

<summary>Issues (7)</summary>

1. **PDDocument leak in convertPdfPageToImage(Book, ...)** — Opens a `PDDocument` and never closes it. Wrap in try/finally or `.use {}` to avoid file-handle exhaustion.
2. **convertPdfToImage(Book, Boolean) is a no-op stub** — Returns `true` without rendering any pages. `saveBookToShelf` treats `true` as success, so PDF imports will produce no images. Either implement the loop or return `false` to signal the gap.
3. **Path traversal in saveBookToShelf** — Constructs storage paths using `book.name + "_" + book.author` with no sanitization. A crafted name like `../../etc` escapes the intended directory. Apply canonical-path validation as done in `FileController`.
4. **Null-pointer crash in saveBookCover** — `source!!` will throw NPE when `getBookSourceStringBySourceURLOpt` returns null (book origin not found). Use safe-call or handle the null case explicitly.
5. **Unused userMutex** — `BaseController` declares a `Mutex()` field but never acquires it. Either protect `saveUserSession`'s read-modify-write of the users file with it, or remove it to avoid confusion.
6. **saveFromRemoteSource duplicates readRemoteSourceFile** — Both methods fetch a URL via `webClient` and return the body. The only difference is the auth check. Consider consolidating.
7. **canEditBookSource / canEditRssSource not wired** — Defined but never invoked from any route or handler. They'll have no effect until a caller is added.

## PDF resource leak in convertPdfPageToImage(Book, ...)

The existing private `convertPdfPageToImage(File, Int, Float)` properly wraps `PDDocument.load` in try/finally with `doc?.close()`. The new public overload `convertPdfPageToImage(Book, Int, Boolean)` opens a `PDDocument` and passes it to `savePdfPageToImage` but has no close call anywhere in its body:

```kotlin
val doc = org.apache.pdfbox.pdmodel.PDDocument.load(localFile)
val renderer = org.apache.pdfbox.rendering.PDFRenderer(doc)
savePdfPageToImage(doc, renderer, pageIndex, dpi, imageFormat, outputFile)
// no doc.close()
```

Each invocation leaks a file handle and the memory for the in-kernel PDF page tree. Under repeated calls (e.g., converting all pages of a book by calling this in a loop), this will exhaust the OS file descriptor limit.

## convertPdfToImage stub and downstream implications

The method body is:
```kotlin
fun convertPdfToImage(book: Book, force: Boolean = false): Boolean {
    return true
}
```

`saveBookToShelf` calls `convertPdfToImage(book)` and checks the boolean:
```kotlin
if (!convertPdfToImage(book)) {
    return Pair(book, "本地PDF书籍转换失败")
}
```

Since the stub always returns `true`, the import path will report success but produce zero page images. The book will be on the shelf with no rendered content. The FEAT-001 findings note acknowledges "convertPdfToImage(Book, Boolean) returns true unconditionally matching JAR bytecode" — so this may be intentional JAR-matching, but it leaves a functional gap for any user importing PDFs.

## Path traversal in saveBookToShelf

```kotlin
val relativeLocalFilePath = Paths.get("storage", "data", userNameSpace,
    book.name + "_" + book.author, tempFile.name).toString()
```

`book.name` and `book.author` come from the HTTP request body (parsed from `context.bodyAsJson`). A malicious payload like `{"name": "../../etc", "author": "passwd", ...}` would construct a path outside the intended storage directory. The `FileController` and `UserController` both validate via canonical-path comparison; this method does not. The same pattern repeats in all three branches (assets, localStore, webdav).

## Null-safety gap in saveBookCover

```kotlin
val source = if (bookSource != null) {
    bookSource
} else {
    getBookSourceStringBySourceURLOpt(book.origin, userNameSpace)
}
// ...
val analyzeUrl = AnalyzeUrl(coverUrl, source = BookSource.fromJson(source!!).getOrNull())
```

When `bookSource` is null (the default) and the book's origin doesn't match any stored source, `getBookSourceStringBySourceURLOpt` returns null. The `!!` operator then throws `KotlinNullPointerException`. The surrounding `try/catch(e: Exception)` catches it, but the failure is silent — `book.coverUrl` is never updated and no error is logged.

## ReturnData.setData signature change

The addition of `msg: String = ""` to `setData` means successful responses now set `errorMsg` to the provided `msg` (or empty string). Previously `setData` hard-coded `errorMsg = ""`. The only new caller using the second parameter is `saveUserBookSources` which passes a summary string. Because `isSuccess = true` in this case, clients that check `isSuccess` first will behave identically — but any client that displays `errorMsg` regardless of success state will now show the batch-import summary as an "error message". This is a semantic oddity rather than a bug, but worth documenting in the API contract.

## BaseController refactoring: saveUserSession and userMutex

The refactored `saveUserSession` now performs its own read-modify-write cycle on the `users.json` storage file:

```kotlin
var userMapJson: JsonObject? = asJsonObject(getStorage("data", "users"))
// ... mutate ...
saveStorage("data", "users", value = userMap)
```

This is a TOCTOU race under concurrent logins: two requests can both read the map, each adds their session, and the second write overwrites the first. The newly-declared `userMutex` field was presumably intended to guard this section but is never acquired. Without locking, token data written by one concurrent login can be silently lost.
