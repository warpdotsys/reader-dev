# Pro-features migration to reader-dev: Foundation, TTS, PDF, File management, and Licensing

This change migrates six feature areas from reader-pro into reader-dev in a single batch: a DB abstraction and CURD interface layer, per-user mutex and LRU cache, MongoDB backup/restore, a file manager controller with path traversal protection, an Edge/Azure WebSocket TTS engine, PDF reading support via PDFBox, a license controller stubbed to "always valid", new scheduled jobs (auto-backup, GC, remote source subscription), expanded user permission fields, `contextPath` routing, and compiled web frontends. The build passes cleanly (Kotlin 1.5.21, Java 8). Vert.x is bumped from 3.8.1 to 3.8.5 with `vertx-auth-common` added.

**Watch for:** Three new `BookController` methods (`convertPdfToImage`, `savePdfPageToImage`, `getSpeakStream`) have no route registration — they are unreachable dead code (confirmed). `FileController.importPreview` omits "pdf" from its supported-extension list while `BookController` import paths accept PDF (confirmed). `BookGroupController` is instantiated in `YueduApi` but never used — routes still delegate to legacy `BookController` methods (confirmed). The `UserController.downloadBackupFile` path-traversal check uses string contains ("..") instead of canonical-path resolution, which can be bypassed on certain platforms (likely). The `TTSService` spin-waits with `Thread.sleep` and allocates a new `OkHttpClient` + WebSocket per request with no pooling (confirmed).

## High-level view

The DB abstraction (`DB` / `JSONTable` / `CURD` interface) wraps the existing `getStorage` / `saveStorage` pattern behind a generic CRUD API. Controllers like `HttpTTSController` and `BookGroupController` use it to eliminate boilerplate. `SQLTable` is a stub that throws `NotImplementedError` on all paths — its presence is harmless but adds dead code.

`FileController` is the most security-sensitive addition: it mediates all user file operations behind a `resolveSecurePath` method that canonicalizes both the base and the resolved path and compares prefixes. This is correct and blocks traversal. However, the parallel `downloadBackupFile` in `UserController` uses only a string-based `contains("..")` check, which is weaker.

The TTS module is a self-contained Java library driving Edge Speech or Azure Speech WebSocket endpoints. It synthesizes SSML and returns raw audio bytes. `BookController.getSpeakStream` wires this into an HTTP endpoint that creates a fresh `TTSService` (and its `OkHttpClient` + WebSocket connection) per request, with no caching, pooling, or rate limiting.

PDF support integrates through PDFBox at every touch point: `Book.isPdf()`, `LocalBook` dispatch, `PdfFile` for chapter listing and text extraction, plus image-rendering endpoints that use `PDFRenderer`. The integration is thorough but the rendering endpoints are unreachable because no routes point to them.

The license system is intentionally inert — `isLicenseValid()` and `checkLicenseFeature()` always return `true`. The ten license-related API routes exist for frontend compatibility but enforce no restrictions.

`contextPath` support in `YueduApi` uses Vert.x `reroute()` to strip a configured prefix. Route registration happens *before* the contextPath handler is added, meaning the prefix-stripping handler sits lower in priority than the API routes — requests without the prefix hit the API directly, which is the intended design.

## Unreachable PDF and TTS endpoints in BookController

Three public methods were added to `BookController` but never wired:

```kotlin
suspend fun convertPdfToImage(context: RoutingContext) { ... }
suspend fun savePdfPageToImage(context: RoutingContext): ReturnData { ... }
suspend fun getSpeakStream(context: RoutingContext) { ... }
```

No corresponding `router.get(...)` or `router.post(...)` call exists in `YueduApi`. These are fully implemented (rendering via `PDFRenderer`, TTS via `TTSService`) but unreachable from any HTTP client.

## FileController path security vs UserController path security

`FileController.resolveSecurePath` does canonical path comparison:

```kotlin
private fun resolveSecurePath(baseDir: File, relativePath: String): File? {
    val resolved = File(baseDir, relativePath).canonicalFile
    val baseDirCanonical = baseDir.canonicalFile
    if (!resolved.path.startsWith(baseDirCanonical.path)) {
        return null
    }
    return resolved
}
```

This is the correct approach and blocks `../` traversal on any platform.

In contrast, `UserController.downloadBackupFile` uses:

```kotlin
if (fileName.contains("..") || fileName.contains("/") || fileName.contains("\\")) {
    context.response().setStatusCode(400).end("文件名不合法")
}
```

This is weaker — it catches the common case but does not handle edge cases like URL-encoded sequences or platform-specific separators. Since `downloadBackupFile` constructs a `File(backupDir, fileName)` from user input, it should use canonical path resolution to be consistent with `FileController`.

## TTS resource lifecycle and spin-wait

`TTSService.sendText` busy-waits:

```java
while (synthesising) {
    log.info("空转等待上一个语音合成");
    Tools.sleep(1);  // Thread.sleep(1000)
}
```

This blocks the calling thread for up to 30 seconds (the `latch.await` timeout) per prior synthesis request. In a server context where `getSpeakStream` can be called concurrently, the blocked threads accumulate.

Furthermore, each invocation of `getSpeakStream` constructs a new `TTSService`, which in turn creates a new `OkHttpClient` and opens a new WebSocket connection. There is no pooling, no singleton, and no cleanup — the WebSocket stays open until the server closes it or GC collects the unreferenced `OkHttpClient` (which has a connection pool with idle timeouts).

## `cacheBookOnServer` sequential fetch

The implementation iterates through every chapter and fetches content synchronously within a single coroutine:

```kotlin
for (chapter in chapterList) {
    ...
    val content = WebBook(bookSource, appConfig.debugLog).getBookContent(...)
    ...
}
```

For a book with 500 chapters, this holds the HTTP connection open for potentially minutes. There is no concurrency, no chunked progress response, and no timeout per chapter. If the upstream source is slow, the Vert.x worker thread is occupied indefinitely.

## Instantiated but unused BookGroupController

```kotlin
val bookGroupController = BookGroupController(coroutineContext)
```

This instance is created in `YueduApi` route setup but no route references it. The existing `bookController.getBookGroups`, `bookController.saveBookGroup`, etc. methods continue to serve the `/reader3/getBookGroups` routes. The new `BookGroupController` implements a CURD-based version of the same logic but it's never called.

## PDF extension missing from `importPreview`

`FileController.importPreview` filters files by:

```kotlin
val supportedExtensions = listOf("txt", "epub", "umd", "cbz")
```

While `BookController.uploadBook` and `importFromLocalPath` now allow:

```kotlin
if (ext != "txt" && ext != "epub" && ext != "umd" && ext != "cbz" && ext != "pdf") { ... }
```

Users who upload a PDF through the file manager and then try to preview-import it will find it filtered out.

## Scheduled job controller instantiation

`autoBackup` and `remoteBookSourceSubUpdateJob` create fresh controller instances:

```kotlin
val bookController = BookController(coroutineContext)
```

These jobs run every 2 hours / 12 hours respectively. Creating a controller per invocation is not expensive but is unusual — if controllers ever carry state (caches, connections), this pattern silently discards it between invocations.
