# Fix pass for 12 review issues (v2)

Three commits address all 12 issues from the first review: missing ExtKt utility functions added, TTS HTTP endpoints implemented in BookController and wired in YueduApi, `saveBookContent` method added, `parseJsonStringList` rewritten with JAR-compatible signature, `SQLTable` now delegates to `JSONTable`, PdfFile converted to class+Companion with `cFile` caching, RemoteWebview integrated into both `ReaderAdapter` and `DefaultAdpater`, `LicenseController` gains `privateKeyContent`/`tryCodeCache`/`backupFileNames` fields, `isLicenseValid` returns `ReturnData`, `updateRemoteSourceSub` accepts `User?`, `checkLicense` scheduled job added, and the CI workflow simplified to compile-only.

**Watch for:** `decryptData` performs base64 decode rather than RSA decryption — any caller expecting actual cryptographic decryption will get plaintext garbage (confirmed). The `checkLicense` scheduled job unconditionally calls `setLicenseValid(true)` even if the license check fails (confirmed). `ttsByTextToSpeechCn` is implemented but unreachable — no dispatch path in `textToSpeech` ever calls it (confirmed).

## High-level view

The ExtKt additions include `getCommand`, which executes arbitrary shell commands via `ProcessBuilder`. No route currently exposes user-controlled input to it, but any future wiring without sanitization is RCE. This mirrors the JAR behavior faithfully.

The TTS endpoints route through a dispatch pattern: `textToSpeech` reads params, looks up the named `HttpTTS` source, then delegates to `ttsByEdge` or `ttsByApi`. The `ttsByTextToSpeechCn` function is implemented but never called — there's no dispatch path that reaches it, making it dead code.

PdfFile is now a class with instance state and a companion that maintains a single cached instance via `cFile`. The companion's static methods match the JAR's API. The single-instance cache means concurrent requests for different PDFs thrash, but this mirrors the JAR's limitation.

The `LicenseController` fields (`privateKeyContent`, `tryCodeCache`, `backupFileNames`) are structural scaffolding — present for API compatibility but not wired to any logic. `decryptData` is base64-decode, not RSA, so the full license crypto workflow cannot be restored without replacing it.

Both `ReaderAdapter` and `DefaultAdpater` contain identical `getStrResponseByRemoteWebview` implementations with the same RemoteWebview delegation. One should delegate to the other.

## `decryptData` as base64 stub

The JAR's `decryptData` performs RSA private-key decryption. The PR's implementation:

```kotlin
fun decryptData(encrypted: String): String {
    return try {
        String(JavaBase64.getDecoder().decode(encrypted), Charsets.UTF_8)
    } catch (e: Exception) {
        ""
    }
}
```

This means `decryptToLicense` → `decryptData` → base64-decode → `gson.fromJson`. If the stored license string is RSA-encrypted (as the JAR intended), this produces garbage. Since the community edition never stores real encrypted licenses, the mismatch is dormant — but it makes the function name actively misleading for anyone reading the code expecting crypto.

## `ttsByTextToSpeechCn` dispatch gap

In `textToSpeech`, the dispatch logic is:

```kotlin
if (url.contains("edge-tts") || httpTTS.name.contains("edge", ignoreCase = true)) {
    ttsByEdge(response, text, params)
} else {
    ttsByApi(response, text, url, params)
}
```

The `ttsByTextToSpeechCn` method is never reached. The JAR likely has a third condition checking for "texttospeech.cn" in the URL. Without it, any HttpTTS source configured with a texttospeech.cn URL will be routed through the generic `ttsByApi` path, which sends a GET request with URL substitution rather than the JSON POST body that `ttsByTextToSpeechCn` implements. This will fail silently for that specific TTS provider.

## `checkLicense` scheduled job control flow

```kotlin
@Scheduled(cron = "0 0 0/6 * * ?")
fun checkLicense() {
    launch(Dispatchers.IO) {
        try {
            val license = getInstalledLicense()
            if (license != null) {
                val licenseController = LicenseController(coroutineContext)
                licenseController.checkLicense(license)
            }
            setLicenseValid(true)  // <-- unconditional
        } catch (e: Exception) {
            logger.error("checkLicense error: {}", e.message)
        }
    }
}
```

`setLicenseValid(true)` executes regardless of whether a license was found or whether `checkLicense` succeeded. The catch block swallows errors without setting `_licenseValid = false`, meaning even corrupt storage leaves the system in "valid" state. For community mode this is the desired behavior (fail-open), but if the license system is ever restored, this pattern becomes a bypass — move `setLicenseValid(true)` inside the success path and add `setLicenseValid(false)` in the catch.
