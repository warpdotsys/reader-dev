# JAR-to-Source Consistency Audit (v2)

Migration of reader-pro-3.2.14.jar features into the `feat/migrate-pro-features` branch. This second pass focuses on remaining discrepancies between the decompiled JAR class signatures and the current source code, after 12 issues from the first pass were fixed.

Watch for: `saveBookConfig` endpoint and method entirely missing from source (confirmed); `onCheckEnd` boolean parameter inverted in JSONTable causing CURD save operations to report existing entities as "new" (confirmed); `Book` entity missing `pdfImageWidth` field and `isLocalPdf()` method (confirmed); `forEachUser` signature diverges from JAR in both suspend behavior and lambda type (confirmed); `createUserBackup` return type and parameter signature differ from JAR (likely intentional simplification, but changes API contract).

## High-level view

The `saveBookConfig` endpoint (`POST /reader3/book/saveBookConfig`) is registered in the JAR but has no counterpart in the source — neither the route nor the controller method exist. This endpoint modifies book-level settings (including `pdfImageWidth`) and is called by the frontend. Its absence means the frontend's book configuration dialog will 404.

The `JSONTable.save()` method passes the `found` flag directly to `onCheckEnd`, but CURD's contract names that parameter `isNew`. When `found = true` (entity exists, was updated), `onCheckEnd` receives `true` for `isNew`, inverting the semantics. Any controller that overrides `onCheckEnd` and branches on `isNew` will execute the wrong path.

The `Book` entity is missing `pdfImageWidth: Float` (with getter/setter) and `isLocalPdf(): Boolean`. Both are used by the absent `saveBookConfig` and by the PDF rendering pipeline in the JAR. The source added `isPdf()` but left out the width config and the local-PDF predicate.

`UserController.forEachUser` in the JAR is a suspend function taking a `suspend CoroutineScope.(User) -> Boolean` callback; the source has a non-suspend function taking `(String, User) -> Unit`. The source's version is only called from scheduled jobs in YueduApi, so the behavioral impact is limited, but the contract change breaks binary compatibility if any external code references this method.

`BookController.createUserBackup` in the JAR returns `File` and accepts three String parameters (with defaults for backup path components). The source returns `Boolean` and takes only `userNameSpace`. The JAR's `backupToWebdav` calls `createUserBackup` to get the File reference for upload; the source's `backupToWebdav` delegates to a `getLastBackFileFromWebdav` + `saveToWebdav` pattern instead, so the mismatch is accommodated by the different flow — but the method is no longer a drop-in replacement for callers expecting the old contract.

Route URLs for File, HttpTTS, TTS, and WebDAV modules were restructured from the JAR's paths (e.g. `/reader3/file/list`, `/reader3/httpTTS/list`, `/reader3/book/tts`, `/reader3/user/downloadBackupFile`) to flatter paths (`/reader3/getFileList`, `/reader3/getHttpTTSList`, `/reader3/textToSpeech`, `/reader3/downloadBackupFile`). This is intentional but breaks API compatibility with any frontend or client pinned to the old URLs.

## Missing `saveBookConfig` method and endpoint

The JAR's `BookController` has:
```
public final Object saveBookConfig(RoutingContext, Continuation<? super ReturnData>)
```

The inner classes reveal it uses `editShelfBook` and modifies `pdfImageWidth` (via `Ref$FloatRef`). The route `POST /reader3/book/saveBookConfig` is registered in the JAR's `YueduApi.initRouter`. Neither the method nor the route exists in the source. The frontend book-config dialog (likely part of simple-web) will call this endpoint.

## `onCheckEnd` boolean inversion in `JSONTable.save()`

```kotlin
// JSONTable.kt line ~78
override fun save(entity: T, onCheckEnd: ..., checker: ...) {
    ...
    var found = false
    for (...) {
        if (checker(obj, entity)) {
            found = true  // entity EXISTS, this is an UPDATE
            break
        }
    }
    ...
    onCheckEnd?.invoke(entity, found, allData)  // BUG: found=true means "existed" but CURD reads it as "isNew"
}
```

The CURD interface declares `onCheckEnd(entity: T, isNew: Boolean, allData: JsonArray)`. When `found = true`, the entity was already present — `isNew` should be `false`. The same inversion exists in `saveMulti`.

The JAR's compiled `JSONTable` uses the same `onCheckEnd` callback and the boolean semantics match the CURD contract (passing `isNew` correctly). The BookGroupController's `onCheckEnd` is currently a no-op, so this bug has no visible effect today — but adding any logic to `onCheckEnd` that distinguishes create from update will behave incorrectly.

## Missing `Book.pdfImageWidth` and `isLocalPdf()`

The JAR's Book class has:
```
private float pdfImageWidth;
public final float getPdfImageWidth();
public final void setPdfImageWidth(float);
public final boolean isLocalPdf();
```

The source's Book data class added `isPdf()` in this PR but omitted `pdfImageWidth` and `isLocalPdf()`. The `pdfImageWidth` field controls the rendered image width when PDF pages are converted to images (used in `savePdfPageToImage` and exposed via `saveBookConfig`). Without it, the PDF rendering pipeline defaults will differ from the JAR's behavior.

## `forEachUser` contract divergence

JAR signature:
```java
public final Object forEachUser(
    Function3<CoroutineScope, User, Continuation<Boolean>, Object>,
    Continuation<Unit>)
```
This is `suspend fun forEachUser(handler: suspend CoroutineScope.(User) -> Boolean)` — the handler is suspend, receives a User (no username string), and returns Boolean (to control iteration).

Source signature:
```kotlin
fun forEachUser(handler: (String, User) -> Unit)
```
Non-suspend, takes username + User, returns Unit.

The source's callers (YueduApi scheduled jobs) don't use the JAR's forEachUser at all — they inline their own user-iteration loops. So this method is currently dead code in practice, but its existence suggests it was part of the internal API.

## `convertPdfToImage` / `savePdfPageToImage` / `getSpeakStream` refactored

These three methods have fundamentally different signatures between JAR and source:

| Method | JAR | Source |
|--------|-----|--------|
| `convertPdfToImage` | `(Book, boolean): boolean` | `suspend (RoutingContext)` |
| `savePdfPageToImage` | `(PDDocument, PDFRenderer, int, float, String, File): void` | `suspend (RoutingContext): ReturnData` |
| `getSpeakStream` | `(HttpTTS, String, int): InputStream` | `suspend (RoutingContext)` |

The source consolidated these into HTTP-route handlers rather than keeping them as internal utility methods called by route handlers. The JAR's `textToSpeech` route handler calls `getSpeakStream(httpTTS, text, speechRate)` internally; the source's `textToSpeech` instead dispatches to `ttsByEdge`/`ttsByApi`/`ttsByTextToSpeechCn` directly. This is a deliberate architectural change that replaces the internal `getSpeakStream` with a new endpoint handler.

The route `/reader3/getSpeakStream` in the source exposes a new direct-to-client TTS synthesis endpoint that didn't exist in the JAR. This is additive.
