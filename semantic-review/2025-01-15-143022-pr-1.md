# Migration of reader-pro-3.2.14.jar features into reader-dev

This PR ports the full feature set of `reader-pro-3.2.14.jar` into the open-source `reader-dev` repository. It introduces new controllers (CURD, BookGroupController, FileController, HttpTTSController, LicenseController), a DB abstraction layer (DB/JSONTable/SQLTable), TTS library classes, PDF handling, MongoDB integration, adapter interfaces, utility classes (LRUCache, UserMutex, RemoteWebview, MongoManager), and numerous new BookController/UserController methods. The approach copies the JAR's architecture faithfully: interface-based CURD, JSON-file-backed storage, per-user namespaces, scheduled jobs, and Edge/Azure TTS via WebSocket.

**Watch for:** Several JAR utility functions are missing entirely (confirmed). The `textToSpeech` endpoint and its helper methods (`ttsByEdge`, `ttsByApi`, `ttsByTextToSpeechCn`, `getHttpTTSByName`) are absent from BookController (confirmed). `SQLTable` is a stub that throws on every operation (confirmed). The complex `parseJsonStringList(File, ...)` overload from ExtKt is replaced with an incompatible simplified version (confirmed). The `checkLicense` scheduled job from YueduApi is absent (confirmed).

## High-level view

The DB layer is structurally complete for JSON-backed storage, but `SQLTable` is a throwing stub — any code path that requests `type = "sql"` will crash at runtime. Since the JAR's `SQLTable` had the same method signatures as `JSONTable` with presumably real SQL logic, this is a functional gap.

The CURD interface and its two consumers (BookGroupController, HttpTTSController) match the JAR's signatures and provide real default-method implementations. FileController covers all 12 methods from the JAR with full logic including path-traversal protection.

The `ExtKt` utility file is missing approximately 8 functions that exist in the JAR: `getInstalledLicense`, `decryptToLicense`, `decryptData`, `getMongoFileStorage`, `readMongoFile`, `saveMongoFile`, `countOccurrences`, `sendEmail`, `getCommand`, and `getStorageFile`. The `parseJsonStringList` function is present but with a different signature (takes `String?` instead of the JAR's `File, Set, Set, int, int, Set, Function1`). Code that calls these missing functions (e.g. LicenseController logic, MongoDB backup/restore, BookSourceController advanced features) will fail to compile or link.

The TTS subsystem is split: the low-level Edge/Azure WebSocket TTS library (`TTSService`, `SSML`, voice enums) is fully ported, but the BookController methods that wire it to HTTP endpoints (`textToSpeech`, `ttsByEdge`, `ttsByApi`, `ttsByTextToSpeechCn`) are absent. The `getSpeakStream` route exists but without the supporting `textToSpeech` endpoint, the full TTS feature is incomplete.

LicenseController is implemented as a community-mode pass-through: all methods return success or "community edition" without performing real cryptographic validation, remote activation, or email verification. This is intentional for an open-source fork but means the `checkLicense` scheduled job was also dropped, creating a signature mismatch with the JAR's YueduApi class.

PdfFile is refactored from an instance-with-companion pattern (caching a single `cFile` instance) to a stateless `object` that takes `InputStream` parameters. The API surface changes: callers must provide InputStreams where the JAR only required `Book` objects. LocalBook integration will need updating if it expects the JAR's companion API.

## Missing ExtKt utility functions

The JAR's `com.htmake.reader.utils.ExtKt` class exports these public static functions that have no counterpart in the PR source:

- `getMongoFileStorage()` — returns `MongoCollection<MongoFile>`, used by MongoDB backup/restore
- `readMongoFile(String)` — reads file content from MongoDB
- `saveMongoFile(String, String)` — persists file content to MongoDB
- `getInstalledLicense(Boolean)` — reads and decrypts the installed license from storage
- `decryptToLicense(String)` — RSA-decrypts a license string to a `License` object
- `decryptData(String)` — generic RSA decryption helper
- `sendEmail(String, String, String)` — sends email (used by `LicenseController.sendCodeToEmail`)
- `getCommand(List<String>, String, String)` — parses command-line-style arguments
- `countOccurrences(String, String)` — counts substring occurrences
- `getStorageFile(String[], String)` — returns a `File` reference for storage path

The PR's `VertExt.kt` has `getStorage` and `saveStorage` but not the `getStorageFile` variant. The `backupToMongodb` and `restoreFromMongodb` methods in BookController are wired as routes but their implementations will fail or be incomplete without `getMongoFileStorage`/`readMongoFile`/`saveMongoFile`.

Additionally, `parseJsonStringList` in the JAR accepts `(File, Set<String>, Set<String>, int, int, Set<String>, Function1<ObjectNode, Boolean>)` — a streaming parser that can filter and page through large JSON array files. The PR replaces this with a trivial `parseJsonStringList(String?)` that deserializes a JSON string to `List<String>`. The `BookSourceController.getUserBookSourceJsonOpt` likely depends on the complex version for efficient source file parsing.

## TTS endpoint gap

The `TTSService`, `SSML`, `VoiceEnum`, `TtsStyleEnum`, `OutputFormat`, `SpeechConfig`, `TtsConstants`, `Tools`, and `TtsException` classes are all present and correctly ported from Java. However, the BookController methods that actually expose TTS to HTTP clients are missing:

```
textToSpeech(RoutingContext)          — the main entry-point, dispatches to ttsByEdge/ttsByApi/ttsByTextToSpeechCn
ttsByEdge(HttpServerResponse, String, Map)
ttsByApi(HttpServerResponse, String, String, Map)
ttsByTextToSpeechCn(HttpServerResponse, String, Map)
getHttpTTSByName(String, String)      — resolves an HttpTTS entity by name from user storage
```

The `getSpeakStream` route is wired in YueduApi and exists in BookController, but `textToSpeech` (which the JAR exposes as a streaming audio endpoint) is not present. Without `textToSpeech`, the web UI's "read aloud" feature won't work even though the underlying WebSocket TTS client is fully implemented.

## SQLTable stub

`SQLTable` throws `NotImplementedError` for every operation. The JAR's decompiled signature shows it has the same method set as JSONTable — meaning it was a real implementation (likely backed by SQLite or a similar embedded DB). The PR's `DB.table()` factory defaults to `"json"`, so normal operation won't hit SQLTable unless explicitly requested. But if any configuration or future feature requests `type = "sql"`, it will crash immediately.

## PdfFile design change

The JAR's `PdfFile` maintains a cached instance (`cFile`) with `book`, `info`, and `cover` fields, lazily parsed. The companion methods (`getChapterList(Book)`, `getContent(Book, BookChapter)`, `upBookInfo(Book, Boolean)`) internally call `getPdfFile(book)` which either returns the cached instance or creates a new one.

The PR's `PdfFile` is a stateless `object` where every method takes an `InputStream` parameter. This means:
- Each call requires the caller to open a new InputStream to the PDF file
- No caching of parsed PDF metadata or document structure
- The API is incompatible with the JAR's companion-style calls

If `LocalBook` or `BookController` code calls `PdfFile.getChapterList(book)` expecting the JAR's interface, compilation will fail.

## LicenseController as community pass-through

The PR implements all 10 endpoint methods from the JAR (`getLicense`, `importLicense`, `generateKeys`, `generateLicense`, `isHostValid`, `decryptLicense`, `activateLicense`, `isLicenseValid`, `checkLicense`, `sendCodeToEmail`, `supplyLicense`) but as stubs that either return success unconditionally or return "community edition not supported". This is a deliberate trade-off for an open-source fork.

Missing from the implementation:
- `privateKeyContent` field (RSA key for decryption)
- `tryCodeCache` field (ACache for email verification codes)
- `backupFileNames` lazy property
- `webClient` usage for remote activation calls
- The `isLicenseValid` route signature matches a `ReturnData`-returning endpoint in the JAR but is a `Boolean`-returning utility in the PR

The `checkLicense` periodic job in YueduApi is also absent — the JAR calls it on a schedule to validate license expiry and phone-home.

## RemoteWebview integration gap

The `RemoteWebview` object is implemented with `getStrResponse(...)` that makes HTTP POST calls to a configurable remote webview API. However, both `DefaultAdpater.getStrResponseByRemoteWebview` and `ReaderAdapter.getStrResponseByRemoteWebview` return `null` unconditionally. The JAR's `ReaderAdapter` delegates to `RemoteWebview.getStrResponse(...)`.

This means that book sources requiring JavaScript/webview rendering will silently get `null` responses instead of actual rendered content, even when `remoteWebviewApi` is configured in `AppConfig`.
