# 原子替换窗口的存储读取一致性

更新：2026-10-05。只使用临时生成存储，不读取用户账号库、正文或生产数据。

## 已复现的缺陷

`saveStorage` 持有文件写锁，将原文件移动为备份后再安装新文件。`getStorage` 原先在取得读锁前检查文件是否存在，因此会在这个很短的窗口直接返回 `null`。在 `data/users.json` 上，这可能让一次正常鉴权看起来没有账号；是机制推断，不能将它直接当作某次真实界面失败的唯一根因。

新回归通过实际生产文件锁与两个生成线程、协调门闩精确控制窗口，不做概率性压力猜测。旧源码的 3 项测试有 1 项实际失败、0 跳过，0.423 秒；断言为 `A reader must not treat the locked replacement gap as missing data`。XML SHA-256 `1da6e7c180ad30a743205de373495f8696b8fe09c0798c377186c55e411594ae`，冻结在忽略的 `build/storage-read-gap-20261005-a/baseline/`。首次反射夹具因 Kotlin 私有方法名称修饰报错，修正后才取得这个真实失败；首次错误不是产品证据。

将存在性检查移入与写入相同的读锁保护范围，不修改路径、JSON 格式、备份流程、用户校验或缺失数据的返回约定。修复后相同 3 项生成测试全部执行通过（0.715 秒）：窗口内的读等待写入完成并返回原格式；真正缺失仍为 `null`；生成 users 的完整性校验继续拒绝篡改。XML SHA-256 `9fd3fc01c74e1a5ce9867dc9b9d953da714e55782db20341293d76fa26377297`，另目录冻结，不覆盖失败。

- `26255c0` 的 Vue 托管运行 37296514253 在甲退出后乙 token 的 `getUserInfo` 被拒绝；保留失败。只改诊断测试的下一源码 `6d937970` 的 Vue 运行 37298826192 已成功，说明前次失败不能凭一次绿灯宣布修好。修复源码 `755bb7d9` 的 Vue 运行 37300753570 与其余三条工作流均成功；下载 21 项实际界面 XML 全部无跳过/失败/错误，其中跨标签 13.733 秒、退出 22.904 秒到完整终点。这证明本轮回归通过，不证明前次失败的唯一根因。

- 未跑原 JAR 新差分、真实认证、真实 Mongo 或生产；已有数据未迁移、删除或覆盖。
