# EPUB Worker 就绪后转移输入候选

状态：可读源码与本机生成测试已执行；本候选自己的正式产物、生成浏览器旅程和真实单书八场景尚未验收。789 的准确 f95d 产物及 S 四/八失败保留，不据本候选单元测试称超时已修复，不发版或部署。

## 已从源码确认 / 候选修改

此前 `expandEpubInWorker` 创建 Worker、安装回调后，立即转移整本 ZIP；虽然已经接收固定 `ready` / `expanding` 消息，却没有以 `ready` 作为发送的前提。S 的首次原样显示在 starting 超时，这使“尚未启动的 Worker 已收到大输入”成为值得单独验证的时序问题，不能据此证明唯一根因。

现在仅在正确、唯一且按序的 `ready` 确认后，转移独占 ArrayBuffer 或复制有效子视图。创建时开始的同一条 15 秒总计时不重置、不另加启动宽限；没有 Worker 预热或提前启动后台进程。取消或超时后，保存的迟到回调也不能复制或发送输入；重复确认拒绝且不能二次转移已分离的输入。最终文件仅在 `expanding` 之后接受，不能由越序的结果伪报成功。传输失败保留真实错误并终止该 Worker。

实际解压 Worker 源码、ZIP 算法、4 KiB 步长、输入/展开/单项/文本/条目限制、60 秒下载、命名空间与 iframe 安全策略不改。没有空实现、页内脚本注入、调高资源限额或改 Java/Kotlin/浏览器依赖版本。打包 Worker 字节是否保持一致须用本候选正式 JAR 再核对。

## 已执行的本机验证

- 定向 Worker / loader 共 37 项通过。六项新增回归覆盖延迟发送及子视图复制、ready 前取消、超时后的迟到确认、实际 structuredClone 转移、越序最终结果与重复确认不二次发送。
- 原有 starting / ready / expanding 三阶段虚拟时钟仍在 15,000 毫秒结束，14,998 / 14,999 毫秒确认不能重置总期限。
- 两项 legacy 下载契约的生成 Worker 替身补齐真实模块已有的 ready / expanding 顺序；它们仍只验证下载、token 与相对路径，不冒充真实浏览器执行。
- 全前端 332 项零失败、零跳过；类型检查成功，Vite 构建成功（11.37 秒）。本机既有依赖不是新的精确 npm ci，正式 CI 必须用锁文件重新执行。
